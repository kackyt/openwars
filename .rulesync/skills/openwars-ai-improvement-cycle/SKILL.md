# OpenWars AI改善サイクル

目的は、ゲーム上の成果を改善し、その理由を計画から実行まで説明できる変更を残すこと。対戦を繰り返す前に、観測できる原因と反証方法を作る。

## まず改善の条件を固定する

- HEAD、ユーザーの未コミット変更、評価対象の実装・バイナリ、マップ・先後・相手・seed・ターン上限を区別する。基準は必ずしもHEADではなく、ユーザーが評価した作業ツリーも含む。
- ユーザーが求める成果を短く記す。「防衛と攻撃」のような同時要件は、同じ対局・同じ時点で成立したかを測る。勝率などの最終成果と、占領維持・到達・初撃などの途中成果を分ける。
- 人間ログの手順は比較材料。兵種列や座標を本番コードへ写さない。ユーザーが要求していない「T15まで」「全seed勝利」などを独自に完了条件へ追加しない。診断用の観測時点はその旨を明示する。
- `reports/<task>/` に短い作業記録を置く。基準実装、今回の仮説、予測する行動差、反証条件、実験結果、採否、採用中の実装、残課題を更新する。途中案を最良の検証済み実装と取り違えない。

## 計画から実行まで、最初の食い違いを追う

指定されたログを読み、敗北後の総数から原因を推測する前に、結果に効く最初の行動差を選ぶ。[ログ分析ガイド](references/log-analysis-guide.md)を使う。

そのEntityについて、次を実際の値でつなぐ。

`盤面・合法手 → 候補列挙 → 計画の役割/対象/初撃時刻 → 生産施設 → 配備任務 → Squad/DAG → 戦術候補 → 選択コマンド → 実行イベント`

値が変わった最初の境界を調べる。対象の再ソート、別Registryによる上書き、キャッシュの失効、合法手の早すぎる除外を先に確認する。そもそも候補が存在しない問題を評価係数で直そうとしない。計画側が正しいとも決めつけず、実行条件と照合する。

同じ対象・役割を複数箇所で決めているなら、正本と更新責務を定める。専用任務が有効な間、無効化された時、汎用処理へ戻る時の境界を明らかにする。

## 因果関係を一つずつ検証する

- 仮説は「この入力で、どの処理が、何を誤り、修正後に何が変わるか」とする。小さな局面・境界テストで修正前の失敗と修正後の成功を確認し、実行イベントまで必要な範囲を検証する。
- 一度に試すのは一つの因果仮説。**一ファイル・一層だけを直すという制限ではない。** 任務の受け渡しなど、複数層を一緒に直さなければ成立しない変更は一組として扱い、受け渡しの不変条件をテストする。無関係な生産・評価・経路変更は混ぜない。
- 最小差分より、原因を除く一貫した設計を優先する。重複する割当や古い上書き規則は削除・置換してよい。既存コードを温存するための補正層を増やさない。
- [評価値ハック排除原則](references/no-hack-principles.md)に従う。合法性、移動/射撃/占領時刻、損失、生産能力を区別し、名前やコメントを付けただけの定数調整で代用しない。
- 既存テストの失敗は、ゲームルールの違反か、変更する旧方針の固定かを切り分ける。前者は修正する。後者はログやルールによる根拠を示して更新し、性能退行を隠すために期待値を緩めない。

## 検証を小さく始め、採用候補だけ広げる

[ベンチマーク実行プロトコル](references/benchmark-protocol.md)に従い、次の証拠が得られてから範囲を広げる。

1. 局面・境界テスト：狙った原因が消えたか。
2. 代表対局の短いトレース：**狙った行動が実際に変わったか**。行動が変わらなければ、その下流の上書きや再計算を調べる。勝敗だけで修正の効否を決めない。
3. 採用候補の12 seed逐次比較：基準と同条件で、最終成果・同時要件・seed別退行を確認する。明らかに反証された案ごとに12 seedを完走しない。
4. 最終状態で `cargo test`、`cargo fmt --all -- --check`、`cargo clippy --all-targets --all-features -- -D warnings`。通過後は、新たな変更や懸念がなければ同じ検証を繰り返さない。

## 採否を決めて収束する

- 予測した行動が変わらない、または要件が悪化した試案は、差分と反証を記録して直前の採用状態へ戻す。ユーザー変更まで巻き戻さない。失敗案へ別仮説を積み重ねない。
- 同じ失敗を繰り返す場合は、新たな全対戦を始める前に責務の図と最初の食い違いへ戻る。前回から何が新しく分かったかがないまま、似た案を再試行しない。
- 成果が改善し、原因に対応する行動差と品質チェックを確認できたら、採用状態を更新する。総合改善と個別seedの退行は併記する。厳守条件に反する案は勝率だけで採用しない。
- 完了判断はユーザーの要件に戻す。必須要件が未達なら改善を続ける。満たした後に、人間と同じ手順や未要求の完全勝利を求めて探索を際限なく延長しない。
- 最終報告は、原因・変更・同条件での成果・残る退行・検証範囲を示す。検証レポート、ベンチマーク生ログ、一時的な試案はローカル保存とし、**通常のコードコミットには含めない**。再現に必要な最小テストfixtureはコードとともに管理する。コミット時は対象ファイルを明示し、ユーザーの指定を優先する。

## 比較ツール

このスキルの `scripts/compare_benchmarks.py` は、各 `seedN.json` に一対局が入る結果を比較する。通常勝利とターン上限判定を分け、欠損・対戦条件の不一致をエラーにする。

```text
python -X utf8 <skill-dir>/scripts/compare_benchmarks.py <baseline-dir> <candidate-dir> --subject V4 --output <local-report.md>
```

`<skill-dir>` は読んでいるスキルのディレクトリ。`--seeds` は検証段階に合わせ、同じAI同士なら `--side 1` または `--side 2` を指定する。固有の同時要件はログ分析ガイドに沿って別途集計する。総合比較ツールだけで両立を証明したことにしない。
