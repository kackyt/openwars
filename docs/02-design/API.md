# API.md - API/インターフェース設計書

> ※ 本プロジェクトはローカル実行のゲームアプリケーションであるため、Web REST APIではなく、Rustクレート間のインターフェース仕様について記述します。

## 1. インターフェース概要

`engine` クレートとプレゼンテーション層（`cli`, `gui`）の間の境界を定義します。
通信は以下の2つのフローで構成されます。

1. **コマンド (UI -> Engine)**: プレイヤーの入力を受けて、ゲーム状態を変更するリクエスト。
2. **イベント (Engine -> UI)**: 状態変更の結果をUIに通知し、描画やアニメーションをトリガーする。

## 2. コマンドフロー (UI -> Engine)

UIクレートは、`engine` クレートで定義された公開関数やシステムを利用してコマンドを発行します。

### 例：ユニットの移動
- UIはプレイヤーのキーボード操作を受け取り、選択されたユニットIDと目標座標を取得。
- `engine` の該当ユースケース（メソッド）またはコマンドキューへリクエストを送信。
- `engine` は移動可能か（ActionPointsが足りているか、障害物がないか等）をバリデーションし、可能であればコンポーネントの状態を更新する。

## 3. イベントフロー (Engine -> UI)

`engine` は `bevy_ecs` の Event 機構を用いて、状態の変化をブロードキャストします。UIはこれを購読（EventReader）して画面を描画します。

### イベント定義例
```rust
pub struct UnitMovedEvent {
    pub entity: Entity,
    pub from: GridPosition,
    pub to: GridPosition,
}

pub struct AttackEvent {
    pub attacker: Entity,
    pub defender: Entity,
    pub damage: u32,
}
```

### 重要な制約: 1フレーム遅延
`main.rs` のループ構造上、入力処理の結果が描画に反映されるのは「次のループ（1フレーム後）」になります。
メニューなどのステートフルなUIを表示・遷移させる際は、イベントを受け取ってエンジン側の更新が完了したことを確認してから遷移させる必要があります。イベントを手動でクリアする処理（`clear()`）の呼出漏れにも注意してください。

## 4. 将来の拡張 (GUI / Tauri)
将来的にTauriを用いたGUIを実装する場合、`engine`へのコマンド呼び出しはTauriのコマンドインターフェース（`#[tauri::command]`）を介して非同期に実行され、状態の更新はフロントエンドへイベント通知される設計を想定しています。
