# Issue #58 侵攻成果を拠点・収入・勝利へ転換する設計

## 1. 背景

Issue #54 と #56 により、V3 は map_3 で敵島への輸送、上陸、交戦まで実行できるようになった。Issue #58 では、その後の戦力運用を敵拠点の占領、収入増加、敵首都への圧力、勝利へ結び付ける。

本作業は計測先行・真因駆動で進める。評価基盤を先に再現可能にし、固定 seed の baseline で確認できた原因だけを修正する。map_3 固有座標、P1/P2 固有分岐、特定 seed 専用の調整は導入しない。

## 2. スコープ

### 2.1 対象

- 固定 seed セットを指定できる評価経路
- P1・P2 が同じターンの行動を完了した後の公平な T30 計測
- Issue #58 専用の合否判定と診断レポート
- 占領スループット、生産投資、戦闘 ROI、侵攻マイルストーンの構造化計測
- 固定 seed による map_1・map_2・map_3 の baseline
- baseline で確認された真因に対する最小限の AI 改善
- 同一条件での変更後評価と回帰確認
- 真因ごとのローカル子 Issue 案

### 2.2 対象外

- Load・Transit・Drop の基本機能再実装
- 複数の敵島への同時侵攻
- V1 輸送 AI の再設計
- map_3 固有の座標・手番・seed に依存する調整
- GitHub 上への子 Issue の実作成

GitHub 子 Issue はユーザー指定により作成せず、`benchmarks/issue-58/child-issue-drafts.md` に単一責務の案として保存する。このため、Issue 本文の「真因ごとに子 Issue を作成する」はローカル案で代替する。

## 3. 採用アプローチ

計測先行・真因駆動を採用する。

1. 評価基盤と診断テレメトリを修正する。
2. AI 戦略ロジックを変更せず baseline を取得する。
3. 仮説ごとに証拠を整理し、真因と否定仮説を分離する。
4. 確認された原因を一つずつ、テスト駆動で修正する。
5. 同じ seed、手番、ターン数で再評価する。
6. map_1・map_2 の回帰と品質ゲートを確認する。

既知の弱点を先に一括修正する方法は、修正効果を原因へ帰属できないため採用しない。侵攻後戦略全体の包括的な再設計も、Issue #72・#80 等と責務が重複するため baseline で必要性が確認されない限り行わない。

## 4. 評価基盤

### 4.1 固定 seed セット

`scripts/eval_matchup.py` に複数 seed の入力を追加する。

- `--seeds 58001,58002,58003,58004`
- 各 seed につき両手番を一戦ずつ実行する。
- `--seed` は後方互換のため単一 seed として維持するが、Issue #58 モードでは `--seeds` を使用する。
- Issue #58 モードでは seed を4個以上必須とし、重複を拒否する。
- seed 一覧は試合結果、Markdown、JSON、`seeds.txt` に記録する。

標準の評価 seed は次の4個とする。

```text
58001
58002
58003
58004
```

### 4.2 公平なターン境界

1ラウンドを次の順序で扱う。

```text
P1 行動
  → P2 行動
  → ラウンド末盤面計測
```

T30 は P1 と P2 の30ターン目の行動が両方完了した直後の盤面とする。途中で勝敗が決定した場合は、決着直後の盤面を最終値とする。

現在の「各 AI 行動前に計測し、同じターン番号の最後の値へ集約する」方式は、T30 が P2 行動前になるため置き換える。

### 4.3 Issue #58 判定

`--criteria issue58` を追加し、少なくとも次を判定する。

- 基準1: 各手番で V3 の平均 ZOC 支配面積が V2 を上回る。
- 基準2: 各手番で V3 の平均ターン収入が V2 以上である。
- 基準3: T15 以降の5ターン移動平均で、V3 のユニット資産価値と収入が基準点から低下し続けない。
- V3=P2 で V3 の平均収入が V2 以上である。
- V3=P2 で V3 の平均拠点数が V2 以上である。
- V3=P2 の固定 seed 試合で、自軍初期島外の拠点を少なくとも一つ獲得する。
- 総合勝率が40%以上である。
- map_3 の平均思考時間が baseline 比50%超で悪化しない。
- map_1・map_2 で baseline 時に PASS だった手番別判定を FAIL へ退行させない。baseline 時に FAIL だった判定は悪化させず、改善状況を参考情報として記録する。

試合エラー、手番バケット欠損、必要メトリクス欠損がある場合は PASS にしない。

### 4.4 成果物保護

Issue #58 モードでは `matchup_report.md` を出力先に指定できないようにする。Markdown と JSON は一時ファイルへ書き込み、成功後に置換する。

成果物は次へ保存する。

```text
benchmarks/issue-58/
  seeds.txt
  baseline-<sha>.md
  baseline-<sha>.json
  result-<sha>.md
  result-<sha>.json
  analysis.md
  child-issue-drafts.md
```

SHA には AI 対象コミットを使用する。加えて working tree 状態、評価スクリプトの内容ハッシュ、MCP サーバーの内容ハッシュ、実行コマンドを記録する。

## 5. 診断テレメトリ

`mcp-server/src/invasion_trace.rs` を、ゲームルールを持たない評価アダプターとして拡張する。既存のドメインイベントと ECS 状態から診断情報を構築し、ルール判定は `engine` に残す。

### 5.1 生産

生産ごとに次を記録する。

- ターン
- プレイヤー
- ユニット種別
- 生産コスト
- 生産位置

これにより、Infantry、Mech、戦闘ユニット、輸送ユニット、高コスト艦への投資額を比較する。

### 5.2 戦闘

攻撃前後のユニットスナップショットと `UnitAttackedEvent` を関連付け、次を記録する。

- 攻撃側・防御側のエンティティ ID
- 攻撃側・防御側のユニット種別
- 攻撃側・防御側のプレイヤー
- 与ダメージと反撃ダメージ
- ゴールド換算した与ダメージ価値と被ダメージ価値

撃破でエンティティが消えた場合も、攻撃前 HP と消滅を使って損害を算出する。Battleship の投資額、与ダメージ価値、勝敗との関係を集計できるようにする。

### 5.3 占領と侵攻マイルストーン

既存の Load、Unload、Attack、CaptureProgress イベントを同じカーゴ ID と対象島で関連付ける。

- 最初の輸送ユニット生産
- 最初の Load
- 最初の Drop
- 最初の交戦
- 最初の占領開始
- 最初の占領完了
- 上陸から占領開始までのターン数
- 上陸した占領要員数
- 占領開始数・完了数
- 初期島外で獲得した拠点数
- 敵首都への到達または占領進行

## 6. baseline と分析

### 6.1 baseline 条件

- Subject: V3
- Baseline: V2
- seed: 58001、58002、58003、58004
- 各 seed で両手番
- 最大30ターン
- map_3: Issue #58 の主要判定
- map_1・map_2: 回帰比較用 baseline

AI 戦略ロジックは変更せず、評価基盤と診断テレメトリだけを追加した状態で取得する。

### 6.2 仮説判定

`analysis.md` で次の仮説を検証する。

| 仮説 | 必要証拠 |
| --- | --- |
| 占領要員が不足している | 生産数、上陸数、占領開始数、輸送容量 |
| 上陸後に部隊が分散する | Drop 後の目標、占領開始 ETA、対象島外への移動 |
| Battleship が過剰投資である | 投資額、与ダメージ価値、戦闘 ROI、勝敗 |
| 護衛戦力が不足している | 占領要員の生存率、上陸後の敵排除率 |
| 敵首都を狙わない | 首都までの ETA、目標選択、首都周辺戦闘 |
| 後攻の立ち上がりが遅い | 生産・Load・Drop・交戦・占領の手番差 |

証拠が十分なものだけを `confirmed` とし、否定できたものは `rejected`、データ不足は `inconclusive` とする。

## 7. AI 改善の上限設計

複数モジュールにまたがる侵攻後の不整合が真因と確認された場合、`engine/src/ai/strategy.rs` で盤面から導出する非永続の `InvasionOutcomeState` を導入する。

概念上、次を保持する。

```text
target_island
landed_capture_units
landed_combat_units
enemy_properties_remaining
capture_in_progress
captured_properties
enemy_capital_position
enemy_combat_power
friendly_combat_power
```

侵攻段階は次とする。

```text
Staging
  → Beachhead
  → SecuringProperties
  → CapitalAssault
  → Completed
```

- `Staging`: 十分な侵攻部隊が上陸していない。
- `Beachhead`: 上陸済みだが占領要員の安全確保が必要。
- `SecuringProperties`: 対象島の敵拠点を連続占領する。
- `CapitalAssault`: 首都へ到達可能な戦力と占領要員が揃った。
- `Completed`: 対象島の敵拠点がなくなった。

### 7.1 モジュール責務

- `engine/src/ai/squad.rs`
  - 降車した占領要員を Capture 部隊へ引き渡す。
  - 占領中または占領地点へ移動中の要員を前線攻撃へ再割当しない。
  - 戦闘要員を占領地点周辺の敵排除・護衛へ割り当てる。
- `engine/src/ai/beam_search.rs`
  - 上陸後の対象島と目標拠点を維持する。
  - 占領可能な状況で局所位置スコアだけを理由に別方向へ逸れる候補を抑制する。
- `engine/src/ai/objectives.rs`
  - 占領中の拠点、到達ターンが短い敵拠点、敵首都の順に決定的な優先順位を提供する。
  - 同点は島 ID と座標で解決する。
- `engine/src/ai/production.rs`
  - 侵攻段階ごとの不足量だけを生産スコアへ反映する。
  - 輸送能力を超える地上部隊の過剰生産を抑制する。
  - 高コスト艦は、到達可能な戦場と正の期待戦闘価値がある場合だけ高評価にする。
  - Battleship 固有の禁止ではなく、コスト、ETA、期待与ダメージで一般化する。

baseline が単一原因だけを示した場合は、この段階モデル全体を導入せず、原因に必要な最小の値オブジェクトと純粋関数だけを実装する。

## 8. エラー処理

Issue #58 モードでは次を実行前に検証する。

- seed が4個以上で重複しない。
- 対象マップ一覧に map_3 が含まれ、Subject=V3、Baseline=V2、最大30ターンの主要条件を満たす。map_1・map_2 は同じ実行または別の回帰実行に含めてよい。
- Markdown と JSON の出力先が指定される。
- `matchup_report.md` を上書きしない。

MCP 起動失敗、ツールエラー、JSON 不正、ゲーム途中停止、必要メトリクス欠損は試合 ERROR として保存する。ERROR を含む評価バケットは FAIL とし、評価プロセスを非ゼロ終了させる。

## 9. テスト戦略

### 9.1 Python

`scripts/test_eval_matchup.py` に次を追加する。

- seed セット解析、重複拒否、4 seed 未満拒否
- 各 seed が両手番へ同じ値で渡されること
- T30 が P1・P2 行動完了後に計測されること
- 収入同値が PASS、ZOC 同値が FAIL であること
- T15 以降の5ターン移動平均判定
- 初期島外拠点獲得判定
- 後攻バケット欠損、試合 ERROR、メトリクス欠損時の FAIL
- baseline/result メタデータ生成
- 占領スループット、生産投資、Battleship ROI 集計

### 9.2 Rust

診断差分計算を純粋関数へ分離し、次をテストする。

- 攻撃前後 HP から与・反撃ダメージ価値を算出できる。
- 撃破でエンティティが消えても損害を計上できる。
- 生産イベントに種別、コスト、プレイヤーが含まれる。
- 占領開始と完了を同じユニット・拠点で関連付けられる。

AI の真因修正ごとに、失敗する単体テストまたは決定的な統合テストを先に追加する。固定 seed の長時間対戦は単体テストへ埋め込まず、評価成果物として分離する。

### 9.3 品質ゲート

```text
python -m unittest scripts.test_eval_matchup
cargo test
cargo clippy --all-targets --all-features -- -D warnings
cargo fmt --all -- --check
```

加えて、同じ seed セットで map_1・map_2・map_3 の変更前後評価を実行する。
